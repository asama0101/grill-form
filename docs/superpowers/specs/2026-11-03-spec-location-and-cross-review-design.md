# SPEC の保存先の統一とクロスレビューの追加 設計書

## 目的と理由

grill-form が作る SPEC に、次の 2 つの問題がある。

- 保存先が、入力フォームで毎回指定する任意のフォルダで、ファイル名も `SPEC-<テーマ>-<日付>.md` である。SPEC と実装計画の置き場が定まらず、後続の作業で SPEC を探せない。
- SPEC を出す前の点検（点検2）は、新しいサブエージェント 1 体が 1 つの視点で読むだけである。SPEC の詰めが甘いまま実装計画に進み、計画で想定内容とのずれが出た。

この設計書は、保存先を superpowers の構成に合わせ、SPEC と計画の対応状況を分かるようにし、点検2を観点の違う複数のレビュアーによるクロスレビューに置き換える。

## 目標

- SPEC の保存先を `<作業フォルダ>/docs/grill-form/specs/` に固定する。フォルダがなければ作る。
- 実装計画の置き場の規約を `<作業フォルダ>/docs/grill-form/plans/` と定める。計画づくりは superpowers:writing-plans が行い、grill-form は計画を作らない。
- SPEC と計画の先頭に `status` を書き、対応が完了したかを分かるようにする。
- 点検2を、5 観点・5 体のクロスレビューに置き換える。

## 非目標

- 計画の作成・保存・状態の更新を、grill-form が実行すること（規約を決めるだけにする）。
- 既存の `SPEC-<テーマ>-<日付>.md` の移行。
- 保存先の変更機能。入力フォームの「保存先」欄と、`spec-path` の `--parent` は削除する。
- 点検1、最終確認フォーム、質問ラウンドの仕組みの変更。
- 質問と回答の履歴を残すこと（これまでどおり、承認後は SPEC の 1 ファイルだけを残す）。

## アンチゴール

- 状態の更新手順が SPEC に書かれず、後続の Claude が `status` を更新できないこと。
- クロスレビューが、指摘を直すたびに終わらずに繰り返されること（再レビューは 1 回まで）。
- SPEC の外に、意味を通じさせるためのファイルが必要になること。

## 決定事項

### 1. 保存先とファイル名

- SPEC: `<作業フォルダ>/docs/grill-form/specs/YYYY-MM-DD-<テーマ>-design.md`。例: `2026-11-03-api-design-design.md`。
- 計画の置き場（規約）: `<作業フォルダ>/docs/grill-form/plans/YYYY-MM-DD-<テーマ>.md`。
- 同名のファイルがあれば、末尾に連番（`-2`、`-3`）を付ける。既存のファイルは上書きしない（今の `spec-path` と同じ）。
- 作業フォルダは、Claude Code を起動したフォルダ（カレントフォルダ）。
- `spec-path --theme T` は、`docs/grill-form/specs/` がなければ作り（作成はここで行う）、SPEC のパスを出力する。SPEC のファイルは作らない。（私の判断）
- 入力フォームの「保存先」欄を削除する。回答 Markdown の `## 保存先` 節、`intake.json` の `dest`、SKILL.md 手順2の保存先に関する記述も削除する。

### 2. 状態（status）

SPEC の先頭（frontmatter）:

```
---
status: 未対応
plan: （未作成）
---
```

計画の先頭:

```
---
status: 未対応
spec: docs/grill-form/specs/<SPEC のファイル名>
---
```

| 対象 | `未対応` になる時点 | `完了` になる時点 |
|---|---|---|
| SPEC | 最終確認で承認され、保存された時 | 対応する実装計画が保存された時 |
| 計画 | 計画が保存された時 | 計画の実装がすべて終わった時 |

- SPEC を `完了` にするとき、`plan:` に計画のパス（作業フォルダからの相対パス）を書く。
- 状態の値は `未対応` と `完了` の 2 つだけにする。（ユーザーの指示）
- 保存するとき、grill-form が SPEC に frontmatter を付け、末尾に次の「後続の手順」節を書く。この節が、状態を更新する担当への指示になる。

```
## 後続の手順
1. 実装計画を作るときは、保存先を docs/grill-form/plans/YYYY-MM-DD-<テーマ>.md にする（フォルダがなければ作る）。計画の先頭に status: 未対応 と spec: <この SPEC のパス> を書く。
2. 計画を保存したら、この SPEC の先頭を status: 完了 にし、plan: に計画のパスを書く。
3. 計画の実装がすべて終わったら、計画の先頭を status: 完了 にする。
```

- writing-plans は既定で `docs/superpowers/plans/` に保存する。SPEC の「後続の手順」が、保存先をこの規約に上書きする指示である。（ユーザーの指示は、スキルの既定より優先される）

### 3. クロスレビュー（点検2の置き換え）

SKILL.md 手順9の点検2を、次のクロスレビューに置き換える。

- 実行時点: 今の点検2と同じ。点検1が通り、SPEC 案をまとめたあと、最終確認のフォームを開く前。
- レビュアー: この会話の文脈を持たない新しいサブエージェント 5 体。互いの結果は見せず、同時に動かす。各体に渡すのは、依頼文・SPEC 案・その体の観点だけ。
- 観点:

| レビュアー | 見る点 |
|---|---|
| 要件の網羅 | 依頼文・参考資料の要求が、SPEC のどこで答えられているか。抜けがないか |
| 計画への落とし込み | SPEC に決まっていないことが残らず、writing-plans が計画を作れるか。計画を作るときに推測が要る箇所はないか |
| 受入条件と矛盾 | 受入条件を第三者が「できた／できていない」と判定できるか。概要・流れ・受入条件・非目標・リスク・決定ログのあいだに矛盾がないか |
| シンプルさ | 同じ目的を、より少ない決定・手順・ロジックで達成できないか。依頼にない機能が入っていないか |
| リスクと非目標 | リスクと非目標に漏れがないか |

- 指摘の扱い:
  - Claude だけで直せるものは、SPEC 案を直す。
  - ユーザーの判断が要るもの（矛盾のどちらを採るか、機能を削るかなど）は、手順4に戻って質問にする。回答後は点検1からやり直す。
  - 直したあとの再レビューは 1 回まで。再レビューは、指摘があった観点のレビュアーだけに行う。（私の判断）
  - 再レビューのあとに残る指摘は、SPEC のリスクに書く。（私の判断）
  - 点検の結果は、最終確認のフォームには出さない（今と同じ）。
- サブエージェントが使えないとき: 今の点検2と同じく、自分で 5 観点を順に読む。
- 依頼文・SPEC 案に秘密情報（トークン・パスワード・個人情報）があれば、サブエージェントに渡す前にマスクする（グローバルの CLAUDE.md の「安全」に従う）。

## 変更の対象

- `plugins/grill-form/skills/grill-form/SKILL.md`: 手順2（保存先の記述の削除）、手順9（点検2 → クロスレビュー）、手順10（保存先・frontmatter・後続の手順）。
- `plugins/grill-form/scripts/grill_form.py`: `spec_path` の保存先と名前の形式、`--parent` の削除、`dest` の削除、保存先節の解析の削除。
- `plugins/grill-form/scripts/grill_form_template.html`: 保存先欄の削除。
- `tests/`: 保存先と名前、`--parent` の削除、保存先欄の削除に合わせて更新。
- `README.md`、`docs/development.md`: 保存先、名前、状態、クロスレビューの説明を更新。

## 受入条件

1. `spec-path --theme api-design` を実行すると、`<カレントフォルダ>/docs/grill-form/specs/<今日の日付>-api-design-design.md` が出力され、`docs/grill-form/specs/` が存在する。SPEC のファイルは作られない。
2. 同じコマンドを、同名のファイルがある状態で実行すると、末尾に `-2` の付いたパスが出力される。既存のファイルは変わらない。
3. `spec-path` に `--parent` を渡すと、引数のエラー（終了コード 2）になる。
4. 入力フォーム（`render --intake`）の HTML に「保存先」欄がない。
5. SKILL.md 手順10の保存手順に、frontmatter（`status: 未対応`、`plan:`）の付与と、「後続の手順」節の追記が書かれている。
6. SKILL.md の手順9に、5 観点・5 体のクロスレビューが書かれ、点検2の記述が残っていない。
7. 既存のテスト（変更前に通っていたもの）のうち、保存先・`--parent`・保存先欄に関わらないものがすべて通る。保存先に関わるテストは、新しい仕様に合わせて更新され、通る。`ruff check` と `ruff format --check` が通る。
8. README と docs/development.md の保存先・名前の説明が、受入条件1〜3と一致している。

## 実装の細部（すべて私の判断）

- 入力フォームの削除範囲: 保存先用の部分（保存先のラジオ付きツリー、パス欄、`dest` の復元と `data.dest !== data.cwd` の分岐、`## 保存先` 節の出力）だけを削除する。参考資料用のツリーは残す。
- frontmatter と「後続の手順」節: 最終確認フォームの `summary` には含めない（プレビューに出さない）。手順10で `<S>` に書くときに、Claude が `summary` の前に frontmatter を、後ろに「後続の手順」節を足す。`grill_form.py` に補助コマンドは足さない。
- 「後続の手順」の中のパス: 保存時に、SPEC のファイル名から計算して具体的なパスを埋める。計画のファイル名は、SPEC のファイル名から末尾の `-design` を除いたもの（日付と連番は SPEC を引き継ぐ）。例: `2026-11-03-api-design-design-2.md` の計画は `2026-11-03-api-design-2.md`。
- 終了コード: `docs/grill-form/specs/` の作成に失敗したとき（権限がない、`docs` が既存のファイルである）は、エラーを標準エラーに出して終了コード 1 にする。`--parent` の削除による引数エラーは 2。
- 再レビューの数え方: ユーザーの判断で手順4に戻った場合は、再レビューの回数を 0 に戻す。戻るたびにユーザーの回答が必要なので、ユーザーの関与なしには繰り返さない。
- 5 体の結果の統合: 同じ箇所への指摘が観点ごとに食い違うとき、特に「シンプルさ」の削減提案が他の観点の指摘（要件の網羅など）と衝突するときは、Claude が選ばず、ユーザーの判断が要る指摘として質問に戻す。
- 受入条件5・6の検証: `tests/test_skill.py`（SKILL.md を読む既存のテスト）に、必須の語句が SKILL.md にあること（`status: 未対応`、`後続の手順`、5 観点の名前）と、点検2の記述がないことを検査するテストを足す。
- 回答 Markdown の古い形式（`## 保存先` 節を含むもの）は、節を無視して受け取る。
